## Milestone briefing

**Goal.** Determine whether OPA's decision ID is generated by the producer in AGG's actual integration and what relationship that ID represents. This guards against treating identifier equality as stronger evidence than the producer supports.

**What we accomplished.** Exactly eight sequential invocations completed, covering unchanged repeated inputs, repeated caller-supplied decision IDs, nested IDs and denied decisions. Each invocation emitted exactly one result and one native decision-log event. All eight pairs agreed on ID, input and expected policy result; no duplicate native IDs were observed across the eight evaluations. Submitted ID sentinels were not copied into the output/log identifier. Raw stdout, stderr, submitted inputs, invocation metadata, image identity and the frozen execution inventory are retained in `results/v1`.

**Challenges.** The saved local checkout was older and had uncommitted work, so the milestone used a separate clone of the supplied checkpoint. An initial test run failed because Docker access was blocked and subprocesses could not find `python`; the corrected environment passed the full suite. Before capture, adversarial evaluator tests and independent review corrected verdict precedence for incomplete and semantically mismatched evidence. The protocol did not change after preregistration. OPA SDK source explicitly permits caller-supplied IDs, so a blanket OPA-generated-ID claim would be incorrect.

**Technical impact.** This adds an experiment, replay verifier, source review and tests. No production schema, correlation logic, runtime, policy or historical experiment changed. Stock exec leaves the SDK DecisionID option empty, triggering fresh random UUID generation. A custom SDK caller can fill that option instead. Current ordinary AGG evidence retains native fields and some custody metadata but does not establish which generation mode produced an arbitrary record.

**Product impact.** A returned ID can support association with a particular authorization evaluation when invocation custody and producer semantics are trustworthy. A caller writing that ID against an execution is still a caller assertion. Neither ID equality nor the response/log pair independently proves execution, enforcement, authenticated identity or target outcome. OPA response and log are two representations of the same evaluation.

**GTM/commercial impact.** The potential buyer value is a more defensible explanation of what an assurance finding proves and where it stops. The potential adoption cost is collecting sufficient producer/configuration context for each integration. Neither buyer demand, differentiation, willingness to pay nor time-to-value was measured here. This result does not justify new infrastructure or a commercial claim of verified control effectiveness.

**What remains unknown.** The sample does not establish universal uniqueness, resistance to all caller influence, behavior across deployments, or an execution-to-CloudTrail relationship. SDK/custom REST behavior was reviewed in source, not tested live. The archived image reports a dirty build suffix; tagged source review does not prove reproducible binary-to-source correspondence. Native labels, versions, declared issuer/namespace and hashes alone do not authenticate the producer or distinguish generation from SDK-supplied values. A production provenance schema is not yet justified by this milestone alone.

**Next recommended milestone.** Review the combined NGINX and OPA evidence to decide whether a minimal identifier-provenance representation is necessary and sufficient. Define the assurance error it must prevent and its falsification criteria before approving implementation. Do not start M9b or M9a-ii yet.
